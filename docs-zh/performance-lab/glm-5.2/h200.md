# H200 上的 GLM-5.2 吞吐量优化 { #optimizing-glm-52-throughput-on-h200 }

## 结论 { #conclusion }

![吞吐量优化结果](../../assets/performance-lab/glm-5.2-h200.png)

zai-org/GLM-5.2-FP8 在 NVIDIA H200x8 上的吞吐量优化推荐配置：

???+ tip "推理服务命令"
    ```bash
    python3 -m sglang.launch_server \
        --model-path zai-org/GLM-5.2-FP8 \
        --tp-size=8 \
        --dp-size=8 \
        --enable-dp-attention \
        --mem-fraction-static=0.85 \
        --moe-a2a-backend=deepep \
        --max-running-requests=256 \
        --kv-cache-dtype=fp8_e4m3
    ```

优化前后的基准测试结果对比：

| 基准测试用例 | 基准配置（未做任何优化的 vLLM） | 优化后 |
|----------|-------------------------------------------|-----------|
| **均衡： 8K 输入 / 1K 输出 (优化目标)** | Total TPS: 5481.90<br>Mean TPOT(ms): 636.24 | Total TPS: 17525.76 <span style="background-color:lightgreen;">(+219.70%)</span><br>Mean TPOT(ms): 217.89 |
| **短上下文 (1K 输入 / 128 输出)** | Total TPS: 13196.90<br>Mean TPOT(ms): 316.73 | Total TPS: 18276.60 <span style="background-color:lightgreen;">(+38.49%)</span><br>Mean TPOT(ms): 211.06 |
| **长上下文 (32K 输入 / 100 输出)** | Total TPS: 10513.68<br>Mean TPOT(ms): 1320.02 | Total TPS: 26433.15 <span style="background-color:lightgreen;">(+151.42%)</span><br>Mean TPOT(ms): 537.26 |
| **生成密集型 (1K 输入 / 2K 输出)** | Total TPS: 2268.18<br>Mean TPOT(ms): 42.11 | Total TPS: 2267.33 <span style="background-color:#ffd6d6;">(-0.04%)</span><br>Mean TPOT(ms): 46.54 |
| **ShareGPT** | Total TPS: 6040.94<br>Mean TPOT(ms): 149.24 | Total TPS: 2845.48 <span style="background-color:#ffd6d6;">(-52.90%)</span><br>Mean TPOT(ms): 331.21 |

!!! note
    1. 基准测试未覆盖所有可能的优化组合。例如，我们会选择默认配置下表现最好的推理引擎作为后续调优的起点。这种剪枝方式得到的是局部最优解，未必是全局最优解。
    2. 其他优化方法取决于具体使用场景，包括最大批大小、调度配置、扩展 KV cache、CUDA graph 等。本文结论可作为进一步针对性优化的起点。
    3. 测试基于特定的硬件和软件环境。推理引擎的改进可能带来新的结论。
    4. 量化可能影响准确率，但对于大多数模型，FP8 量化的准确率下降可控制在 1% 以内。详情参见[评估结果](https://github.com/Tencent/AngelSlim/blob/main/README_en.md#-benchmark)。因此，强烈建议在低延迟推理服务场景中使用 FP8 量化。
    5. 推荐配置针对高并发、中长输入场景调优（以 8K 输入 / 1K 输出工作负载为基准）。对于 ShareGPT 等短输入、短输出的对话工作负载，其性能低于单纯使用张量并行，因为 DP-attention 和 DeepEP 优化面向长序列，短请求无法摊薄这些优化的额外开销（参见“其他基准测试用例”中的 ShareGPT）。这一取舍符合 GLM-5.2 的目标场景：其较强的编程能力使编程 Agent 推理服务成为主要使用场景，而该场景通常具有较长上下文，恰好适合本配置。

如有遗漏或需要根据最新变化更新的内容，请[告诉我们](https://github.com/gpustack/gpustack/issues/new/choose)。

### 基准测试方法 { #benchmark-method }

本项目使用 GPUStack 的一键基准测试功能评估推理服务工作负载。本文中的基准测试均通过该流程执行。

GPUStack 的基准测试通过封装项目 [benchmark-runner](https://github.com/gpustack/benchmark-runner)，基于 [guidellm](https://github.com/vllm-project/guidellm) 实现。

对于以下基准测试配置，GPUStack 负责模型部署、基准测试任务提交和结果收集。

!!! warning "分块预填充过大会导致内存不足"
    在此配置下，将 `--chunked-prefill-size` 设置为 **16384 或 32768 会触发内存不足错误并崩溃**：增大分块预填充大小会提高激活值的预留空间，内存规划器会从 KV-cache 预算中扣除这部分空间，导致剩余容量不足以容纳约 700B 的 FP8 权重和 KV cache。只有 `8192`（以及默认值）能够运行，两者的性能差异处于测量噪声范围内。**对于 8K 输入，调整分块预填充大小无法提升吞吐量，因此推荐配置保留默认值。**
