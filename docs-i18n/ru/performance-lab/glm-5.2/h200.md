# Оптимизация пропускной способности GLM-5.2 на H200 { #optimizing-glm-52-throughput-on-h200 }

## Вывод { #conclusion }

![Результат оптимизации пропускной способности](../../assets/performance-lab/glm-5.2-h200.png)

Рекомендуемая конфигурация для оптимизации пропускной способности zai-org/GLM-5.2-FP8 на NVIDIA H200x8:

???+ tip "Команда обслуживания модели"
    ```bash
    python3 -m sglang.launch_server \
        --model-path zai-org/GLM-5.2-FP8 \
        --tp-size=8 \
        --dp-size=8 \
        --enable-dp-attention \
        --mem-fraction-static=0.85 \
        --moe-a2a-backend=deepep \
        --max-running-requests=256 \
        --kv-cache-dtype=fp8_e4m3
    ```

Сравнение результатов бенчмарков до и после оптимизации:

| Сценарий бенчмарка | базовая конфигурация (vLLM без оптимизации) | После оптимизации |
|----------|-------------------------------------------|-----------|
| **Balanced: 8K входных / 1K выходных (цель оптимизации)** | Общий TPS: 5481.90<br>Среднее TPOT(ms): 636.24 | Общий TPS: 17525.76 <span style="background-color:lightgreen;">(+219.70%)</span><br>Среднее TPOT(ms): 217.89 |
| **Короткий контекст (1K входных / 128 выходных)** | Общий TPS: 13196.90<br>Среднее TPOT(ms): 316.73 | Общий TPS: 18276.60 <span style="background-color:lightgreen;">(+38.49%)</span><br>Среднее TPOT(ms): 211.06 |
| **Длинный контекст (32K входных / 100 выходных)** | Общий TPS: 10513.68<br>Среднее TPOT(ms): 1320.02 | Общий TPS: 26433.15 <span style="background-color:lightgreen;">(+151.42%)</span><br>Среднее TPOT(ms): 537.26 |
| **Интенсивная генерация (1K входных / 2K выходных)** | Общий TPS: 2268.18<br>Среднее TPOT(ms): 42.11 | Общий TPS: 2267.33 <span style="background-color:#ffd6d6;">(-0.04%)</span><br>Среднее TPOT(ms): 46.54 |
| **ShareGPT** | Общий TPS: 6040.94<br>Среднее TPOT(ms): 149.24 | Общий TPS: 2845.48 <span style="background-color:#ffd6d6;">(-52.90%)</span><br>Среднее TPOT(ms): 331.21 |

!!! note
    1. Наши бенчмарки не охватывают все возможные сочетания оптимизаций. Например, отправной точкой дальнейшей настройки становится движок инференса с лучшей производительностью при настройках по умолчанию. Такое отсечение вариантов даёт локальный оптимум, который может не совпадать с глобальным.
    2. Есть и другие методы оптимизации, зависящие от сценария использования: максимальный размер батча, настройки планировщика, расширенный KV-кэш, CUDA graph и т. д. Выводы этого документа могут служить отправной точкой для более целенаправленной оптимизации.
    3. Тесты проводились на определённых аппаратных и программных конфигурациях. Развитие движков инференса может привести к новым выводам.
    4. Квантизация может влиять на точность, однако для большинства моделей FP8 обеспечивает снижение точности менее чем на 1%. Подробности см. в [результатах оценки](https://github.com/Tencent/AngelSlim/blob/main/README_en.md#-benchmark). Поэтому для обслуживания с низкой задержкой настоятельно рекомендуется квантизация FP8.
    5. Рекомендуемая конфигурация настроена на высокую конкурентность и входы средней или большой длины (опорная нагрузка: 8K входных / 1K выходных токенов). В диалоговых нагрузках с короткими входами и выходами, таких как ShareGPT, она уступает обычному тензорному параллелизму: оптимизации DP-attention и DeepEP рассчитаны на длинные последовательности, а короткие запросы не компенсируют их накладные расходы (см. ShareGPT в разделе других бенчмарков). Этот компромисс подходит целевому применению GLM-5.2: сильные возможности программирования делают обслуживание агентов разработки основным сценарием, где контекст преимущественно длинный — именно на него и рассчитана эта конфигурация.

Если что-то упущено или требуется обновление с учётом новых изменений, [сообщите нам](https://github.com/gpustack/gpustack/issues/new/choose).

### Методика бенчмарка { #benchmark-method }

В этом проекте используется функция запуска бенчмарка GPUStack одним щелчком для нагрузок обслуживания моделей. Бенчмарки этого документа выполнялись именно таким способом.

Бенчмарки GPUStack реализованы на основе [guidellm](https://github.com/vllm-project/guidellm) через проект-обёртку [benchmark-runner](https://github.com/gpustack/benchmark-runner).

Для перечисленных ниже конфигураций GPUStack выполняет развёртывание модели, отправку заданий бенчмарка и сбор результатов.

!!! warning "Нехватка памяти при большом блоке prefill"
    Установка `--chunked-prefill-size` в **16384 или 32768 вызывает сбой из-за нехватки памяти** в этой конфигурации. Больший размер блока увеличивает резерв для активаций, который планировщик памяти вычитает из бюджета KV-кэша; оставшейся памяти недостаточно для весов FP8 размера ~700B вместе с KV-кэшем. Работают только `8192` и значение по умолчанию; различие между ними находится в пределах шума. **При входе 8K размер блока prefill не даёт прироста пропускной способности, поэтому в рекомендуемой конфигурации оставлен по умолчанию.**
