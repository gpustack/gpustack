# Наблюдательность { #observability }

Отслеживайте метрики GPUStack с помощью Prometheus и Grafana и используйте журналы и трассировки инференса для анализа отдельных запросов.

## Обзор { #overview }

GPUStack предоставляет полный набор показателей для обслуживания моделей и управления ресурсами графического процессора. Благодаря интеграции Prometheus и Grafana пользователи могут собирать, хранить и визуализировать эти показатели в режиме реального времени, обеспечивая эффективный мониторинг и устранение неполадок.

## Встроенный мониторинг модели { #native-model-monitoring }

Откройте имя развёртывания в **Model Service → Deployments**. Доступны вкладки Overview, Monitoring, Instances, GPU Resources и Configuration. Группы мониторинга раскрываются независимо и используют общие фильтры времени, экземпляров и ролей PD.

- Графики используют метрики движка. Отсутствующие значения не заменяются метриками шлюза. Задержки PD помечены ролью источника и относятся к локальному подзапросу, а не автоматически ко всему клиентскому запросу.
- Поддерживаемые статистики задержки: Avg, P50, P95 и P99. Строка статистики охватывает выбранный интервал, точки графика — указанный более короткий интервал расчёта скорости. Пропуски не заменяются нулями; неподдерживаемые, неприменимые, ошибочные и устаревшие данные различаются.
- История GPU и узлов использует стабильные идентификаторы с владельцем. Для новых рядов истории обновите Worker. Последние отчёты старых Worker доступны, но непроверенная история не восстанавливается по индексам GPU. Физические показатели включают другие нагрузки на общем устройстве или узле.
- История движка охватывает текущие экземпляры и наблюдаемые поколения источников; история оборудования — связанные сейчас устройства с зафиксированным владельцем. Это не полный аудит прежних размещений.

Для мониторинга моделей, перенаправления на дашборд модели и мониторинга тестов требуется роль владельца организации (Owner) или администратора платформы. GPUStack также проверяет доступ к запрошенному развёртыванию или тесту и связанным ресурсам.

Доступ к мониторингу Worker и GPU и перенаправлению на их дашборды определяется видимостью ресурсов. Участники организации могут использовать эти API для доступных им ресурсов. Прокси Grafana и Prometheus проверяют собственные права доступа.

API: `GET /v2/models/{id}/metrics` и `GET /v2/models/{id}/resource-metrics`. Они принимают только заданные фильтры, а не клиентский PromQL. Графики, таблицы и CSV используют одни и те же разрешённые результаты.

## Встроенная возможность наблюдения (по умолчанию) { #built-in-observability-default }

По умолчанию GPUStack запускается со встроенным Prometheus и Grafana. Вы можете получить к ним доступ через:

- **Prometheus**: `http://your_gpustack_server_host_ip/prometheus`
- **Графана**: `http://your_gpustack_server_host_ip/grafana`

Встроенный Grafana настроен на анонимный доступ к средству просмотра и имеет отключенную форму входа. По умолчанию учетные данные администратора остаются `admin`/`grafana`.

## Внешняя наблюдаемость (необязательно) { #external-observability-optional }

Если вам нужен внешний стек Prometheus/Grafana, мы рекомендуем использовать предоставленные файлы Docker Compose:

Выполните следующие команды, чтобы клонировать последнюю стабильную версию:

```bash
LATEST_TAG=$(
    curl -s "https://api.github.com/repos/gpustack/gpustack/releases" \
    | grep '"tag_name"' \
    | sed -E 's/.*"tag_name": "([^"]+)".*/\1/' \
    | grep -Ev 'rc|beta|alpha|preview' \
    | head -1
)
echo "Latest stable release: $LATEST_TAG"
git clone -b "$LATEST_TAG" https://github.com/gpustack/gpustack.git
cd gpustack/docker-compose
```

Перед началом установите `GPUSTACK_GRAFANA_URL` для доступного через браузер URL-адреса Grafana (а не имени хоста только для контейнера, такого как `grafana`).

Запустите внешний Prometheus/Grafana (это отключает встроенный стек):

```bash
sudo docker compose -f docker-compose.external-observability.yaml up -d
```

Если у вас уже есть внешний стек Prometheus/Grafana, вы можете настроить его вручную:

1. **Настроить Prometheus для очистки метрик GPUStack**
   Добавьте цели для конечной точки метрик GPUStack (по умолчанию `:10161`) и конечной точки обнаружения воркеров. Пример:

   ```yaml
   scrape_configs:
     - job_name: gpustack-worker-discovery
       scrape_interval: 5s
       http_sd_configs:
         - url: "http://<gpustack_server_host>:10161/metrics/targets"
           refresh_interval: 1m
     - job_name: gpustack-server
       scrape_interval: 10s
       static_configs:
         - targets: ["<gpustack_server_host>:10161"]
   ```

   Воркеры в режиме прокси `tunnel` достижимы только через прямой прокси-сервер GPUStack (порт по умолчанию `30079`), который аутентифицирует каждый передаваемый запрос. Чтобы собирать метрики этих воркеров, добавьте задание, которое предъявляет ключ API GPUStack (создайте его в интерфейсе и скопируйте без изменений — сгенерированный ключ выглядит как `gpustack_<access_key>_<secret_key>`) в качестве учётных данных прокси-перехода:

   ```yaml
     - job_name: gpustack-proxy-worker-discovery
       scrape_interval: 5s
       proxy_url: "http://<gpustack_server_host>:30079"
       authorization:
         credentials: "<gpustack_api_key>"
       http_sd_configs:
         - url: "http://<gpustack_server_host>:10161/metrics/proxy-targets"
           refresh_interval: 1m
   ```
2. **Импортировать информационные панели GPUStack в Grafana**
   Используйте информационные панели, представленные в каталоге `docker-compose/grafana/grafana_dashboards/`, в качестве отправной точки.
3. **Укажите GPUStack на свой Grafana**
   Установите `GPUSTACK_GRAFANA_URL` для внешнего URL-адреса Grafana, чтобы перенаправление панели управления работало. Это должен быть URL-адрес, доступный браузеру.

## Доступ к метрикам { #accessing-metrics }

- **Конечная точка показателей GPUStack**:
  Доступ к метрикам по адресу `http://<gpustack_server_host>:10161/metrics`
- **Целевые показатели рабочих метрик GPUStack**:
  Доступ к метрикам по адресу `http://<gpustack_server_host>:10161/metrics/targets`
- **Интерфейс Прометея**:
  Получите доступ к Prometheus через `http://<host>:19090` по умолчанию или через порт, настроенный `--builtin-prometheus-port` / `GPUSTACK_BUILTIN_PROMETHEUS_PORT`.
- **Grafana UI**:
  Получите доступ к Grafana через `http://<host>:13000` по умолчанию или через порт, настроенный `--builtin-grafana-port` / `GPUSTACK_BUILTIN_GRAFANA_PORT`. Встроенный Grafana настроен на анонимный доступ к программе просмотра с отключенной формой входа. По умолчанию учетные данные администратора остаются `admin`/`grafana`.

## Журналы и трассировки инференса { #inference-logs-and-traces }

Чтобы найти журналы и трассировки инференса, используйте заголовок ответа `X-GPUStack-Request-Id`. Встроенный шлюз добавляет его, когда настроены журналы или трассировки. Серверы Docker по умолчанию отправляют трассировки во встроенный Tempo. Серверные релизы Helm по умолчанию развёртывают отдельный экземпляр Tempo. Экспорт журналов настраивается отдельно и требует указать конечную точку для журналов.

| Назначение или настройка трассировки | Docker | Helm |
| --- | --- | --- |
| Встроенный Tempo | По умолчанию на сервере | По умолчанию в серверном релизе |
| Внешний приёмник OTLP/gRPC | Установите `GPUSTACK_TRACE_OTLP_ENDPOINT` | Установите `tracing.endpoint` |
| Срок хранения блоков во встроенном Tempo (по умолчанию `168h`) | Установите `GPUSTACK_BUILTIN_TEMPO_RETENTION` | Установите `tracing.tempo.retention` |
| Отключено | Установите `GPUSTACK_DISABLE_TRACING=true` | Установите `tracing.enabled=false` |

Tempo удаляет устаревшие блоки при периодической очистке. Срок хранения определяет допустимый возраст блока. Общий расход диска зависит от объёма поступающих трассировок и места, занятого журналом предзаписи (WAL), уплотнением и блоками, ожидающими удаления.

Чтобы оценить объём хранимых блоков, умножьте число поступающих трассировок в секунду на среднее число байтов блоков на диске в расчёте на трассировку и на срок хранения в секундах. Для примера расчёта предположим 10 запросов в секунду, выборку 100%, одну трассировку на каждый запрос в выборке и 1 000 байт блоков на трассировку. Получится около 864 МБ блоков в день или 6,05 ГБ за семь дней. Если для примера добавить 50% запаса, потребуется около 9,1 ГБ. Чтобы определить нужный объём и запас, при типичной нагрузке измерьте размер блоков на трассировку и пиковый объём места под WAL, уплотнение и блоки, ожидающие удаления.

Вкладка `Request Tracing` в сведениях о развёртывании сначала выполняет поиск за последние 24 часа. Для просмотра трассировок нужна роль владельца организации или права администратора платформы. GPUStack применяет те же правила видимости моделей, что и для метрик развёртывания. Перелистывайте результаты или вставьте идентификатор запроса или трассировки в том виде, в котором он указан в GPUStack или Tempo. Если настроен экспорт журналов, скопируйте идентификатор из сведений о запросе и найдите его в системе журналирования. Для внешнего Tempo задайте адрес запросов через `GPUSTACK_TRACE_QUERY_URL` или `tracing.queryURL`.

Когда экспорт журналов включён, сервер и воркеры записывают единый поток JSON в консоль контейнера. Alloy считывает этот поток и журналы движков поддерживаемых форматов. Чтобы проверить отброшенные записи, смотрите метрику Alloy `otelcol_processor_filter_logs_filtered_total` для компонента `engine_format` или `higress_format`. Фильтр движка отбрасывает отдельные текстовые строки без распознаваемого префикса журнала.

При стандартном запуске vLLM и SGLang GPUStack автоматически настраивает включённый экспорт логов (`vLLM >= 0.10.1`, `SGLang >= 0.5.9`) и экспорт трассировок для управляемых образов раннеров (`vLLM >= 0.17.0`, `SGLang >= 0.5.12`). Рецепты управляемого PD Router применяют поддерживаемые ими настройки наблюдаемости по умолчанию. Старые или пользовательские образы сохраняют прежнее поведение запуска и продолжают работать с явными настройками телеметрии, которые всегда имеют приоритет.

Каждый компонент трассировки отправляет спаны непосредственно выбранному приёмнику. Адрес приёма журналов должен быть доступен компонентам, которые их экспортируют. Адрес приёма трассировок должен быть доступен серверу, воркерам, шлюзам и контейнерам инференса, которые их экспортируют. Для приёма используется незашифрованный gRPC, поэтому выбирайте адрес в доверенной сети. При переключении на внешний приёмник или отключении трассировки встроенный Tempo останавливается.

### Настройка Docker { #configure-docker }

1. Чтобы включить экспорт журналов, задайте `GPUSTACK_LOG_OTLP_ENDPOINT=http://<collector-host>:4318/v1/logs` на сервере и на каждом отдельном воркере, который экспортирует журналы. Подключите сокет `/var/run/docker.sock:/var/run/docker.sock` и используйте драйвер журналирования с поддержкой `docker logs`.
2. Чтобы отправлять трассировки внешнему приёмнику, задайте `GPUSTACK_TRACE_OTLP_ENDPOINT=<collector-host>:4317` на сервере и каждом отдельном воркере. Чтобы использовать встроенный Tempo с удалёнными воркерами, см. [Включение трассировки на существующих воркерах Docker](../upgrade/cluster.md#enable-tracing-on-existing-docker-workers).
3. Замените `<collector-host>` именем или адресом, доступным из этих контейнеров. Передайте переменные через `docker run -e` либо в секции `environment` файла Compose, затем пересоздайте контейнеры.

В Docker Tempo и Alloy работают в контейнере GPUStack. Tempo хранит WAL и блоки в `<data_dir>/tempo` и по умолчанию принимает как запросы, так и приём OTLP только на интерфейсе loopback (`127.0.0.1`). Отдельные воркеры Docker автоматически пересылают локальные спаны воркера и движков через аутентифицированный API приёма трассировок сервера без публикации порта `4317`. Файлы трассировок сохраняются вместе с томом данных сервера. Чтобы изменить срок хранения блоков, задайте `GPUSTACK_BUILTIN_TEMPO_RETENTION` на сервере и пересоздайте контейнер. Чтобы вместо этого принимать спаны OTLP напрямую от удалённых воркеров в доверенной сети, задайте `GPUSTACK_BUILTIN_TEMPO_OTLP_LISTEN_ADDRESS` на сервере.

### Настройка Helm { #configure-helm }

1. Настройте адреса приёмников в values каждого релиза GPUStack. Параметр `logging.endpoint` включает экспорт журналов, а `tracing.endpoint` задаёт внешний приёмник трассировок. Релизы только с воркерами могут использовать приёмник сервера, указав `tracing.endpoint`.

   ```yaml
   logging:
     endpoint: "http://<collector-host>:4318/v1/logs"
   tracing:
     endpoint: "<collector-host>:4317"
   ```

2. Замените `<collector-host>` адресом приёмника и обновите релиз Helm. Если Collector находится в другом пространстве имён, используйте DNS-имя Service с указанием пространства имён.

Встроенный шлюз Higress по умолчанию записывает журналы доступа в формате JSON. Чтобы поменять формат, задайте `higress-core.meshConfig.accessLogEncoding` и `higress-core.meshConfig.accessLogFormat` в values Helm.

Образы Tempo и Alloy используют `global.hub` со значением по умолчанию `docker.io`. При зеркалировании в частный реестр сохраните пути репозиториев `grafana/tempo` и `grafana/alloy`.

Чарт запускает Tempo отдельно от подов сервера и по умолчанию монтирует `emptyDir` в `/var/tempo`. При замене пода Tempo трассировки на этом томе теряются. Чтобы сохранять трассировки при замене подов, укажите в `tracing.tempo.existingClaim` существующий PVC в пространстве имён релиза. Том должен быть доступен на запись пользователю или группе с идентификатором `10001`. Чтобы изменить срок хранения блоков, задайте `tracing.tempo.retention` и обновите релиз. При пустом или недопустимом значении срока хранения используется `168h`.

Все поды сервера отправляют запросы во встроенный Tempo по адресу `https://<release>-tempo.<namespace>.svc.<cluster-domain>:3200` с взаимной TLS-аутентификацией, включая релизы с одним сервером. По умолчанию чарт создаёт TLS Secret для запросов. Воркеры и движки инференса отправляют трассировки на порт OTLP/gRPC `4317` сервиса.

Для развёртываний GitOps создайте Secret в пространстве имён серверного релиза и задайте его имя в `tracing.tempo.queryTLSSecretName`. Включите `ca.crt`, `server.crt`, `server.key`, `client.crt` и `client.key`. Сертификат сервера должен покрывать `<release>-tempo.<namespace>.svc.<cluster-domain>`. Для обновления сертификатов сервера и клиента используйте один CA. Создайте новый Secret и обновите его имя в значениях Helm, чтобы перезапустить поды Tempo и сервера с обновлёнными сертификатами.

После изменения адреса приёмника трассировок перезапустите или повторно разверните работающие экземпляры моделей.

### Маскирование данных в экспортируемых журналах { #redact-exported-logs }

Перед экспортом Alloy может заменить совпадения в тексте записи, стеке исключения и поле `path` на `***`. Укажите список непустых регулярных выражений RE2. Пустой список отключает маскирование. Идентификаторы запроса, трассировки и спана остаются доступными для сопоставления записей.

Для Docker передайте `GPUSTACK_LOG_REDACT_PATTERNS` как массив строк JSON каждому контейнеру, экспортирующему журналы. В примере маскируются адреса электронной почты и мобильные номера материкового Китая.

```bash
GPUSTACK_LOG_REDACT_PATTERNS='["(?i)[A-Z0-9._%+-]+@[A-Z0-9.-]+[.][A-Z]{2,}","\\b1[3-9][0-9]{9}\\b"]'
```

Для Helm задайте эквивалентный список YAML в каждом релизе, экспортирующем журналы.

```yaml
logging:
  redactPatterns:
    - '(?i)[A-Z0-9._%+-]+@[A-Z0-9.-]+[.][A-Z]{2,}'
    - '\b1[3-9][0-9]{9}\b'
```

Чтобы применить правила, пересоздайте контейнеры Docker или обновите релиз Helm. Проверьте экспортированные записи в системе хранения журналов по `request_id`. Правила действуют на новые записи, экспортируемые Alloy под управлением GPUStack. Исходные записи по-прежнему доступны через `docker logs`, `kubectl logs` или файлы журналов среды выполнения. Правила не затрагивают уже экспортированные записи и трассировки. Некорректные правила могут остановить экспорт журналов Alloy, при этом GPUStack продолжит обслуживать запросы.

### Поиск запроса { #look-up-a-request }

1. Отправьте запрос к запущенной чат-модели и сохраните заголовки ответа. Замените `<gpustack-host>`, `<api-key>` и `<model-name>` значениями из вашего развёртывания. О правах на инференс см. [Управление ключами API](api-key-management.md).

   ```bash
   curl --silent --show-error --no-buffer \
     --dump-header response-headers.txt \
     'http://<gpustack-host>/v1/chat/completions' \
     --header 'Authorization: Bearer <api-key>' \
     --header 'Content-Type: application/json' \
     --data '{"model":"<model-name>","messages":[{"role":"user","content":"Reply with one word."}],"max_tokens":8,"stream":true}'

   grep -i '^X-GPUStack-Request-Id:' response-headers.txt
   ```

2. В системе хранения журналов задайте диапазон времени вокруг запроса и отфильтруйте записи по атрибуту `request_id`. Используйте атрибут ресурса OTLP `service.name`, чтобы выбрать источник, например `higress`, `gpustack.server` или `gpustack.engine`. Если есть поля `worker_id`, `model_instance_id` и `role`, сузьте по ним результаты.
3. Если запись содержит OTLP Trace ID, по нему можно получить трассировку из системы хранения трассировок. При включённой трассировке идентификатор запроса GPUStack также можно искать по атрибуту спана `gpustack.request_id`, даже если экспорт журналов отключён.

### Пример с Loki и Grafana { #example-with-loki-and-grafana }

1. Для Loki с [включённым приёмом OTLP и структурированными метаданными](https://grafana.com/docs/loki/latest/send-data/otel/) задайте в `GPUSTACK_LOG_OTLP_ENDPOINT` или `logging.endpoint` полный URL приёмника, например `http://<loki-host>:3100/otlp/v1/logs`. Для трассировок задайте в `GPUSTACK_TRACE_OTLP_ENDPOINT` или `tracing.endpoint` адрес Tempo OTLP/gRPC, доступный отправителям спанов. Настройте источники данных Grafana, указав HTTP URL для запросов к Loki и Tempo.
2. В Grafana откройте `Explore`, выберите Loki, укажите диапазон времени запроса и замените `<request-id>` значением заголовка ответа `X-GPUStack-Request-Id`. При стандартном сопоставлении OTLP в Loki `service.name` становится меткой потока `service_name`, а `request_id` сохраняется в структурированных метаданных.

   ```logql
   {service_name=~"higress|gpustack[.](server|worker|engine)"} | request_id="<request-id>"
   ```

   Чтобы сузить результаты до записей, содержащих нужное поле, добавьте `| worker_id="<worker-id>"` или `| model_instance_id="<instance-id>"`.
3. Если результат содержит `trace_id`, скопируйте его в поле запроса `TraceQL` источника данных Tempo. Чтобы открывать трассировку прямо из результата поиска по журналам, настройте в Loki [производное поле](https://grafana.com/docs/grafana/latest/datasources/loki/configure/#derived-fields) типа `Label` с шаблоном `^trace_id$` и внутренней ссылкой на источник данных Tempo. В качестве запроса укажите `${__value.raw}`.

Настройте хранение данных и управление доступом во внешней системе. Если пользователи арендаторов могут запрашивать эти данные, обеспечьте изоляцию арендаторов в этой системе.

!!! tip "Поиск журналов движков PD"

    Для SGLang Mooncake используйте `request_id`, чтобы найти журналы обоих движков, и `pd_attempt_id`, чтобы различать попытки отправки запроса. Для vLLM NIXL найдите входную запись по `request_id` и затем ищите её `pd_coordinator_id` в журналах обоих движков. Если этого поля нет во входной записи, сузьте поиск в журнале Prefill по времени запроса и экземпляру и скопируйте `pd_coordinator_id` из подтверждённого совпадения.

## Миграция со старых настроек создания сообщений { #migration-from-older-compose-setups }

Если вы ранее использовали Docker Compose для запуска Prometheus/Grafana вместе с GPUStack:

- **Сохранять внешнюю наблюдаемость (рекомендуется для непрерывности)**:
  Оставьте существующие контейнеры Prometheus/Grafana работающими. Обновите цели очистки Prometheus до новой конечной точки метрик GPUStack и установите `GPUSTACK_GRAFANA_URL` для существующей Grafana.

- **Переключиться на встроенную наблюдаемость**:
  Остановите старые контейнеры Prometheus/Grafana, затем используйте последнюю версию `docker-compose.server.yaml` (только GPUStack). Встроенная Grafana/Prometheus возьмет верх. Исторические метрики из старого Prometheus не будут перенесены, если вы не сохраните старый стек только для чтения.

## Настройка сопоставления метрик { #customizing-metrics-mapping }

GPUStack поддерживает динамическую настройку сопоставления метрик через свой API конфигурации. Это позволяет вам обновить способ сопоставления показателей механизма выполнения с метриками GPUStack без перезапуска службы. Конфигурация управляется централизованно на сервере, и к ней можно получить доступ или изменить ее через HTTP API.

### Конечные точки API { #api-endpoints }

- **Получить текущую конфигурацию метрик**

  - ПОЛУЧИТЬ `http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/config`
  - Возвращает текущую конфигурацию сопоставления метрик в формате JSON.

- **Обновить конфигурацию метрик**

  - ПОСТ `http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/config`
  - Принимает полезную нагрузку JSON для обновления конфигурации сопоставления метрик. Изменения вступают в силу немедленно для всех воркеров.

- **Получить конфигурацию метрик по умолчанию**
  - ПОЛУЧИТЬ `http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/default-config`
  - Возвращает конфигурацию сопоставления метрик по умолчанию в формате JSON, что полезно для справки или сброса.

### Пример использования { #example-usage }

**Получить текущую конфигурацию:**

```bash
curl http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/config
```

**Обновить конфигурацию:**

```bash
curl -X POST http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/config \
     -H "Content-Type: application/json" \
     -d @custom_metrics_config.json
```

_(где `custom_metrics_config.json` — ваш новый файл конфигурации)_

**Получить конфигурацию по умолчанию:**

```bash
curl http://<gpustack_server_host>:<gpustack_server_port>/v2/metrics/default-config
```

> **Примечание**: Конфигурация должна быть предоставлена в допустимом формате JSON.
