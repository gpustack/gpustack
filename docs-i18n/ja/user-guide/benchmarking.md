# ベンチマーク { #benchmarking }

GPUStack は、実行中のモデルインスタンスを対象にベンチマークを実行できます。Worker が専用のベンチマークコンテナイメージで実行し、結果とログは Worker に保存されます。

## 前提条件 { #prerequisites }

- モデルインスタンスが実行中で、正常に動作していること。

### ルートベンチマークのゲートウェイアドレス { #route-benchmark-gateway-address }

ルートベンチマークでは、実行する Worker から到達可能な Higress のベース URL（`/v1` を含まない）を次の順序で解決します。

1. 実行する Worker が所属するクラスターの `server_url`。
2. Server の `server_external_url`。
3. 作成リクエストのオリジン。ただし、Server の `trusted_hosts` で明示的に許可されている必要があります。

リクエストのオリジンへのフォールバックでは、ワイルドカードは使用できません。ホスト名のみの指定では標準の HTTP/HTTPS ポートだけが許可されます。カスタムポートは `gateway.example:8443` のように明示してください。URL にパスプレフィックスがある場合、前段のプロキシで Higress への転送前に取り除く必要があります。

ターゲットはベンチマークの作成時に固定されます。変更した URL を使用するには、ベンチマークを再作成してください。進捗報告には引き続き Worker の管理アドレスを使用します。

## ベンチマークの作成 { #create-benchmark }

1. `Benchmarks` ページに移動します。
2. `Add Benchmark` をクリックします。
3. インスタンスを選択し、構成を入力します。
4. `Save` ボタンをクリックします。

### ShareGPT ワークロードの長さ { #sharegpt-workload-lengths }

組み込みの ShareGPT データセットでは、入力トークンの最小長、最大長、または両方を必要に応じて設定できます。GPUStack は、トークナイザーで数えた長さが指定範囲内の初回プロンプトを保持します。出力トークン長は任意です。指定すると、保持されたすべてのプロンプトに同じ最大長を要求します。省略すると、各プロンプトはデータセット内の参照回答の長さを使用します。範囲に一致するプロンプトがない場合は、ベンチマークリクエストを送信する前に実行が失敗します。

## ベンチマーク結果の表示 { #view-benchmark-results }

1. `Benchmarks` ページに移動します。
2. 表示するベンチマークを探します。
3. ベンチマーク名をクリックして、結果と構成のスナップショットを表示します。

## 保存された監視データ { #saved-monitoring }

GPUStack は新しいベンチマークの監視データを Server のデータベースに保存します。既定では組み込み PostgreSQL を使用し、`--database-url` で接続先を指定できます。デプロイのリソースを削除した後も、**Stages and Monitoring** でベンチマーク全体や測定段階ごとの保存済みグラフを表示できます。元のメトリクスに欠測がある場合、アーカイブは一部のみを含むことがあります。アーカイブされたハードウェアの詳細を閲覧できるユーザーには、保存状態とともに圧縮後のサイズが表示されます。ベンチマークの結果はアーカイブの有無にかかわらず表示できます。

ルートベンチマークは作成時に、選択したデプロイで稼働中のレプリカを記録します。GPUStack が記録済みレプリカの再起動、リソースの再割り当て、または削除を検出すると、そのベンチマークのライブ監視は利用できなくなります。アーカイブは変更前の保存対象データを保持し、一部のみをカバーしていることを示します。

アーカイブは圧縮して保存されます。実行ごとのサイズ上限は圧縮前と圧縮後の両方に適用され、既定値は 256 MiB です。約 6 分のベンチマーク 2 件を使った容量測定では、通常のデプロイは約 177 KiB、PD デプロイは約 528 KiB の圧縮データになりました。規模の大きなベンチマークでは、アーカイブも大きくなることがあります。データベースの容量計画とバックアップにアーカイブを含めてください。

プラットフォーム管理者は **Benchmarks** ページの **Archive Storage** で全体の保存容量を設定できます。既定では上限なし（`0`）です。上限を設定すると、圧縮後のバイト数を全組織で合算します。1 つの組織が空き容量を使い切ると、すべての組織で容量が増える保存が停止します。最後に正常に保存したデータは引き続き閲覧できます。

保存するたびに、圧縮済みアーカイブを 1 つのデータベース文で書き込みます。MySQL 互換データベースを使う場合は、有効な `max_allowed_packet` を確認し、SQL エンコードとメタデータの領域を確保できるよう `--benchmark-archive-max-run-bytes` をパケット上限より小さく設定してください。[MySQL のパケット制限](https://dev.mysql.com/doc/refman/8.0/en/packet-too-large.html) · [OceanBase のパケット制限](https://en.oceanbase.com/docs/common-oceanbase-database-10000000003681766)

確定済みアーカイブを再修復するには、前回の試行が終了してから少なくともアーカイブの保存間隔（既定で 60 秒）が経過する必要があります。

## ベンチマーク結果のエクスポート { #export-benchmark-results }

1. `Benchmarks` ページに移動します。
2. エクスポートするベンチマークを探します。
3. エクスポートする実行を 1 つ以上選択します。
4. `Export` ボタンをクリックして結果をダウンロードします。

## ベンチマークの編集 { #edit-benchmark }

1. `Benchmarks` ページに移動します。
2. 編集するベンチマークを探します。
3. `Operations` 列の `Edit` ボタンをクリックします。
4. 必要に応じて名前と説明を変更します。
5. `Save` ボタンをクリックします。

## ベンチマークの削除 { #delete-benchmark }

1. `Benchmarks` ページに移動します。
2. 削除するベンチマークを探します。
3. `Operations` 列の `Delete` ボタンをクリックします。
4. 削除を確認します。

## プライベート CA を使用する HTTPS Server でのベンチマーク { #benchmarks-on-an-https-server-with-a-private-ca }

進捗報告とルート推論は Worker の TLS ポリシーに従います。Worker で `GPUSTACK_INSECURE_TLS` または `insecure_tls` 構成オプション（`--insecure-tls`）が有効でない限り、証明書検証は有効です。ベンチマーク専用の TLS 設定はありません。

いずれかの入口が HTTPS を使用し、検証が有効な場合、Worker は信頼する CA バンドルをファイル内容としてベンチマークコンテナに注入します。Worker にインポートしたプライベート CA も含まれます（[追加の信頼する CA](../installation/installation.md#additional-trusted-cas)を参照）。進捗クライアントは `--progress-ca-cert` を使用し、HTTPS 推論は `SSL_CERT_FILE` を通じて注入されたバンドルを使用してバックエンドの検証を有効にします。管理アドレスが HTTP でも、HTTPS ゲートウェイ用の CA は注入されます。

Worker が明示的に検証をスキップする場合、ベンチマークは両方の通信で検証をスキップし、CA バンドルを注入しません。検証が必要な HTTPS 推論でバンドルを読み取れない場合、別の信頼ストアを使用せず、起動を拒否します。進捗報告のみの場合は引き続きベストエフォートで動作し、報告の失敗をログに記録しても測定結果は破棄しません。
